The ASRock BC-250 is a crypto-mining board built around a cut-down
variant of the PlayStation 5's APU: RDNA2, 24 compute units stock (40 after
[unlock](https://github.com/duggasco/bc250-40cu-unlock)), 16 GB of
unified memory. The boards were dumped on the surplus market, and they
are now some of the cheapest 16 GB compute you can put on a desk. (Well,
at least they were, until popularized by mainstream YouTubers; prices
have risen from around $100 to sometimes over $300.)

Several people have already demonstrated that this board can be deployed for LLM inference ([akandr/bc250](https://github.com/akandr/bc250), [Cirius1792/bc250-cluster-ansible](https://github.com/Cirius1792/bc250-cluster-ansible), [wdonega/bc250-llm-setup](https://github.com/wdonega/bc250-llm-setup), [a write-up by Ciro Lucio Tecce](https://ciroluciotecce.it/en/posts/bc250-cluster-inferenza-locale/)).
I was curious whether you could also run ML training workloads. As I also wanted to get my hands a little dirty with Kubernetes, a project idea was born: **Can the BC-250 serve a multi-user JupyterHub on Kubernetes with GPU-accelerated PyTorch and remote access over HTTPS?**

Unfortunately, the BC-250 is hardware that AMD's own ML stack refuses to touch. The GPU
reports as **gfx1013**, which ROCm does not support; I had to resort
to OpenCL through a [third-party backend](https://github.com/artyom-beilis/pytorch_dlprim).
This turned out to be a rabbit hole in itself; at the end of it, I managed to push ML training performance by 2.5× through
profiling and fixing the OpenCL stack.

The project lives in three repositories, and this post is the summary of
all three:

- [**pytorch-gpu-bc250**](https://github.com/mxreyer/pytorch-gpu-bc250): getting
  PyTorch onto the GPU in the first place, plus the benchmark against
  cloud GPUs.
- [**bc250-jupyterhub-opencl-k3s**](https://github.com/mxreyer/bc250-jupyterhub-opencl-k3s):
  serving that GPU as JupyterHub notebooks from single-node Kubernetes.
- [**pytorch-dlprim-gfx1013**](https://github.com/mxreyer/pytorch-dlprim-gfx1013): patching the OpenCL backend for PyTorch, pytorch_dlprim,
  to work correctly and run fast on the BC-250 under Mesa's rusticl driver.

## Objectives

1. **Get PyTorch onto the GPU** without ROCm.
2. **Serve it to more than one person** — real accounts, persistent
   storage, notebooks in a browser.
3. **Learn Kubernetes properly** by operating something real, in plain
   manifests rather than a Helm chart.
4. **Measure it honestly** against cloud GPUs, rather than hand-waving
   about "good enough".
5. **See how far we can push performance** by playing with the OpenCL stack.

## The four cornerstones

### OpenCL instead of ROCm

ROCm is a dead end on gfx1013, so the GPU is reached through
**rusticl**, Mesa's OpenCL implementation, with the out-of-tree
[**pytorch_dlprim**
backend](https://github.com/artyom-beilis/pytorch_dlprim) (it installs as the
`pytorch_ocl` package) exposing it to
PyTorch as `ocl:0`. This turned out to be a strategic win beyond just
working: the OpenCL path needs only the DRI render node
(`/dev/dri/renderD128`), not ROCm's `/dev/kfd`, which makes handing the
GPU to a container dramatically simpler.

### Two fixes to make training work

Out of the box, inference ran and training didn't. Every kernel that
reduces values across a work-group — softmax, cross-entropy, bias
gradients — failed to *compile*.

The cause is a supply-chain mismatch, not a bug in anyone's code. Those
kernels call the OpenCL 2.0 `work_group_reduce_add()` built-ins, and
rusticl only declares them when it detects Mesa's own patched fork of
libclc. Fedora ships plain upstream libclc, so the built-ins vanish.

`pytorch_ocl`'s own dependency already had a portable fallback — a
hand-written reduction using local memory and barriers, needing nothing
past OpenCL 1.2 — sitting behind a `CUSTOM_REDUCE` flag that defaults to
off. The entire fix is flipping that flag and rebuilding one Python
extension. Nothing on the host is touched. The step-by-step version is
the [setup guide in pytorch-gpu-bc250](https://github.com/mxreyer/pytorch-gpu-bc250/blob/main/SETUP.md).

Fedora's libclc has a second problem: its SPIR-V library ships an empty
body for `__clc_flush_denormal_if_not_supported`, so every kernel that
uses `sin`, `cos`, `fma` or `remquo` fails to link. In PyTorch terms
that is `torch.randn` on the device. The notebook image therefore drops
Mesa's maintained libclc fork in over Fedora's, pinned by checksum; see
the [notebook image README](https://github.com/mxreyer/bc250-jupyterhub-opencl-k3s/blob/main/k8s/jupyterhub/notebook-image/README.md).

### The GPU inside an unprivileged pod

The lazy way to give a container a GPU is a `hostPath` mount. That makes
the device file visible, but the kernel's device cgroup still blocks I/O
on it; the usual workaround, `privileged: true`, fixes that by handing
the notebook the keys to every device on the box.

The right tool is a **device plugin** — a small DaemonSet that advertises
the render node to the kubelet as a schedulable resource. Pods *request*
`devic.es/dri` and the kubelet wires it in with exactly the right
permission and nothing more. Only the plugin runs privileged; every
notebook pod stays unprivileged. Requesting a real resource also means a
user pod won't schedule at all if the GPU is unavailable — no silent
fallback to CPU that you discover three hours into a training run.

### JupyterHub that other people can actually use

k3s (single-node upstream Kubernetes) runs a JupyterHub whose spawner
turns "user logs in" into a Kubernetes API call: a per-user pod plus a
per-user 10 GB persistent volume, created on demand and culled after an
hour idle so the GPU is freed. Users self-register and an admin approves
them. A Tailscale sidecar inside the Hub pod terminates real HTTPS for
remote access, in userspace, with no extra privileges. Every manifest,
both images and the full walkthrough are in
[bc250-jupyterhub-opencl-k3s](https://github.com/mxreyer/bc250-jupyterhub-opencl-k3s).

## Benchmark

Identical workload everywhere — **ResNet-9 on CIFAR-10**, 16 epochs, batch
128, FP32. The BC-250 was measured at 24 CUs, at 40 CUs, at 40 CUs with
the GPU clocked up to 2.0 GHz, and at that clock with the performance improvements
from [pytorch-dlprim-gfx1013](https://github.com/mxreyer/pytorch-dlprim-gfx1013)
(what ships in the notebook image); cloud cards get a second run with mixed
precision (`--amp`) for their realistic best case. The BC-250's nearest
counterpart is `DLPRIM_CONV_FP16=1`: fp16 inside the convolution kernels,
fp32 everywhere else. The harness, every result file and the full tables
are in
[pytorch-gpu-bc250's BENCHMARK.md](https://github.com/mxreyer/pytorch-gpu-bc250/blob/main/BENCHMARK.md).

**Training throughput**

| Platform | Precision | img/s | vs BC-250 40 CU |
| --- | --- | ---: | ---: |
| BC-250, CPU only | fp32 | 70 | 0.09× |
| BC-250, 24 CU @ 1.5 GHz | fp32 | 532 | 0.68× |
| **BC-250, 40 CU @ 1.5 GHz** | **fp32** | **786** | **1.0×** |
| BC-250, 40 CU @ 2.0 GHz | fp32 | 919 | 1.17× |
| **BC-250, 40 CU @ 2.0 GHz, fixed** | **fp32** | **2,337** | **2.97×** |
| BC-250, same, `DLPRIM_CONV_FP16=1` | fp16 conv inner loop | 2,992 | 3.81× |
| T4 (Colab) | fp32 | 2,294 | 2.9× |
| T4 (Colab) | amp | 4,441 | 5.7× |
| A100 (Colab) | fp32 | 7,377 | 9.4× |
| A100 (Colab) | amp | 18,690 | 24× |

**Inference throughput** (batch 128)

| Platform | Precision | img/s | vs BC-250 40 CU |
| --- | --- | ---: | ---: |
| **BC-250, 40 CU @ 1.5 GHz** | **fp32** | **3,892** | **1.0×** |
| BC-250, 40 CU @ 2.0 GHz | fp32 | 4,489 | 1.15× |
| **BC-250, 40 CU @ 2.0 GHz, fixed** | **fp32** | **7,130** | **1.83×** |
| BC-250, same, `DLPRIM_CONV_FP16=1` | fp16 conv inner loop | 10,508 | 2.70× |
| T4 (Colab) | fp32 | 7,217 | 1.9× |
| T4 (Colab) | amp | 7,355 | 1.9× |
| A100 (Colab) | amp | 49,612 | 13× |

Three things stand out.

**Accuracy lands in the same place everywhere** — 0.922 to 0.927 across
every platform. The OpenCL stack is numerically correct, which is the
result that matters most.

**Neither of the BC-250 unlocks scales linearly.** Going 24 → 40 CUs
bought 1.48× for 1.67× the cores; 1.5 → 2.0 GHz bought 1.17× for 1.33×
the clock. Still, the two unlocks together are worth 1.73× over the
stock 24 CU config, which is free performance.

**The initially observed gap to the cloud T4 was software, not silicon.**
At 40 CUs and 2.0 GHz the BC-250 is theoretically a ~10.2 TFLOP/s FP32
part — on paper ahead of a T4's 8.1. For training, the fixes from
[profiling the OpenCL stack](https://github.com/mxreyer/pytorch-dlprim-gfx1013)
are worth **~2.5×** (919 → 2,337) at fp32
and **~3.3×** with the fp16 conv inner loop, which closes the fp32
training gap against the T4 outright: 2,337 vs 2,294 img/s. The inference
gap between the BC-250 with 40 CUs @ 2.0 GHz and the T4 at fp32 was ~1.6×; the
software fixes moved this to **within 2%**.

### Where the 2.5× came from

Profiling a ResNet-9 training step showed
89% of it going to convolution, nearly all of that in three Winograd
kernels, so that is where the work went. The biggest single win was
getting rid of atomics. The backward kernels combine partial results
with floating-point atomic adds, which no RDNA GPU before RDNA3 has in
hardware, so each one turned into a compare-and-swap retry loop that ate
39% of the backward-filter kernel. Within one slice of the work every
output has a single writer, so each slice now writes its own scratch
plane and a small kernel adds the planes up afterwards. Other changes
fixed memory access patterns where neighbouring lanes read far-apart
addresses (one BatchNorm reduction ran at 13 GB/s on a 351 GB/s part),
prefetched the next slice's loads before the current multiply, retuned a
work-splitting heuristic that left 24 of the 40 CUs idle on some layers,
and dropped shared-memory padding that kept a second work-group from
fitting on each CU. In the repo's own step-timing harness, which leaves
out data loading, the series takes training from 916 to 2,436 img/s.
Gradients still match CPU references on every ResNet-9 layer shape. Each
change comes with a write-up ready to send upstream to `dlprimitives`,
and the [patch-by-patch table](https://github.com/mxreyer/pytorch-dlprim-gfx1013#the-patches)
shows what each one bought.

## Verdict

For surplus mining hardware running on a driver stack nobody intended for
compute, matching a cloud T4 in fp32 training and landing within 2% of it
in fp32 inference is a good outcome. Getting it to run at all came down to one
build flag and a swapped-in libclc; getting it there took profiling the OpenCL stack and fixing
what the profile found — the host-side unlocks were worth 1.73×, the
software fixes another 2.5× on top.

It is not a cloud GPU replacement. There are no tensor cores and no
autocast — the fp16 convolution mode is the nearest thing, and it is
opt-in for a reason — and the kernel library is still maturing. If you
need to train fast, rent an A100 — it is 8× quicker with mixed precision,
3.2× at fp32.

What it *is* very good at is being **always-on and yours**. No session
limits, no idle timeouts disconnecting you, no per-hour meter, no upload
step. For fine-tuning small models, running inference, teaching, and
learning Kubernetes on something with real consequences, a permanently
available 16 GB GPU under your desk beats a faster one you have to keep
re-renting.
